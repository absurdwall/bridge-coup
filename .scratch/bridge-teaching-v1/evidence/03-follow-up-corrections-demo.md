# 03 · 追问、信息修正与重新分析演示

- 日期：2026-09-23
- 应用：从本票工作流与 Mac UI 源码构建的独立临时 `.app`，以免和同一工作区同期出现的其他 ticket 源码冲突。
- Runtime：官方 Codex CLI `0.156.1`，app-server stdio；本次模型 `gpt-6-astra`。
- 证据范围：三次真实模型响应分别覆盖计划、追问、修正后重新分析。牌局沿用 Ticket 01 的合成牌例，不是用户实际打过的牌，也不代表教学质量已全面验收。

## 输入

- 庄家：南家；定约：4♥；首攻：♠5。
- 北家：♠Q83 ♥A876 ♦KJ2 ♣K54。
- 南家：♠AK4 ♥KQJ4 ♦AQ7 ♣A92。
- 东、西：未知。
- 计分：IMP。

## 演示流程

1. **实时计划：**模型使用两手已录入手牌、定约与首攻，并明确说明东西家持牌未知。响应按未知分布给出成约路线。
2. **实时追问：**问题询问“如果东家确有五张将牌，为什么建议路线仍接受一墩将吃？”，另在“条件假设”栏录入“假设东家有五张将牌（未确认；只作条件讨论）”。模型把该条件标为假设，解释只在条件成立时采用的分支，并再次说明未知旁门牌不能预先确定。回答引用了当前做庄计划与原牌面上下文。
3. **修正后重新分析：**将首攻从 ♠5 改为 ♥5。界面立即将原计划及其追问标为过期，并停用追问入口；用户重新生成后，新的真实回答明确使用 ♥5 为首攻。旧计划和旧追问仍在历史区并保持过期标记。

## 确定性检查

独立运行 `DeclarerPlanRequestBuilderTests` 与 `DeclarerPlanWorkflowTests`：9 项通过。覆盖可见牌和未知手牌边界、条件假设标注、同计划上下文、失败重试复用追问 ID、修改后的旧结果过期、迟到响应丢弃，以及新版本不继承旧追问历史。

此次验证期间，工作区同时出现了其他 ticket 的未跟踪源文件和测试；它们含有两个 `BridgeCard` 定义，且部分测试引用尚不存在的截图/DDS 类型。因而仓库根目录的完整 SwiftPM 构建与测试被这些并行工作挡住。为验证本票，9 项核心检查和上述临时 Mac app 均只从本票需要的源文件隔离构建，没有更改或加入那些文件。
