## What the failed outputs establish

The authorized snapshot supplies the relevant facts, and the output errors are checkable against them:

- **Trick arithmetic / omission:** `short-2-r1/play/decision-0001/decision.json` shows 3NT, North `CQ72`, South `CAK864`, `DAK`, `HA63`, and `SA94`. The initial plan lists seven winners, says one more makes the ninth, and omits the available North CQ. This is an objective count/resource error despite the instruction to reconcile tricks already won with remaining sources.
- **Card ranking / false contingency:** `short-2-r2/play/decision-0005..0006` and `short-3-r3/play/decision-0003` show South CA/CK and North CQ. The model calls leading to CQ a finesse against the lower CJ, or says CQ may lose if a defender overtakes it. No defender club can beat CQ in those states. In contrast, `short-4-r1` uses “finesse” loosely for the same physically sound lead and its certain winner; its grader accepts it. A false losing line or conditional winner claim is material; the bare label is not automatically so.
- **Physical/card-state errors:** `short-2-r3` says North can duck the opening DQ while South retains both DAK, although South must follow with one honor; `short-3-r2` proposes CA then CK while preserving North CQ, although North must follow to both plays; and `short-4-r3/decision-0007` says South can win with HA after South has already played H3 on that trick. These contradict basic follow-suit, consumption, or play-order facts in the supplied snapshot.
- **History/remaining-resource errors:** `short-3-r1` and `short-4-r3` later abandon club winners still represented in the current hands and/or already exposed defender cards. For example `short-4-r3/decision-0011` has South `CK8`, no remaining defenders' clubs (the prior event history accounts for them), and North has no clubs; the plan says not to count further club tricks beyond CK, excluding the established C8. This is a snapshot/history reconciliation failure, not a missing-field defect.
- **Plan/action consistency:** `short-3-r2/decision-0004` selects a low club while retaining a plan that directs CQ now; other decisions keep known-impossible plan steps. There are examples where continuing a plan is sound, so the problem is selective failure to reconcile rather than a missing continuity channel.

These examples are directly visible from the saved request and response pairs. I found no evidence in these completed artifacts that the engine applied an illegal card, failed to include the authorized hands/current trick/history/effective plan, or substituted an answer. The run summaries report legal execution, real model actions, no retries, and complete successful request capture. Short-4-r1 is only a per-run quality pass: its run summary keeps coverage `pending` (consumed honors and entry opportunities observed, but no post-two-honors facet), so it does not establish matrix/acceptance coverage. `review-work/initial-request-comparison.json` independently shows the first five compared requests have equal prompt content, tools, schema order, requested `gpt-6-luna` Medium/all_turns controls (excluding per-item IDs/cache/metadata); the metadata caveat means this cannot prove opaque service-side routing behavior. This evidence weakens prompt/config drift and zero reasoning-token theories, but cannot reveal internal model behavior.

## Remaining source/contract concern: generation order

There is a concrete **consistency issue**, but not a demonstrated schema-validity failure:

- `DeclarerInstructions.txt:8-29` orders work as facts, plan validation/reassessment, then current winner/card and public reason.
- Its `OUTPUT FORMAT` at `:31-38` enumerates `publicReason`, `selectedCard`, then `plan`.
- `Expert.swift:250-258` intentionally emits schema properties in `publicReason`, `plan`, `selectedCard` order, with the comment that current reason should precede future advice. This differs from both the prescribed decision process and the format enumeration. The serialized JSON schema is syntactically valid; property ordering does not change its JSON meaning, and the captured actions validate. Thus this is not an invalid-output or missing-data contract defect.

A bounded candidate changing both the instruction's output enumeration and schema property order to `plan → selectedCard → publicReason` would make generation order agree with the stated decision process and is reasonable to test as a controlled alignment change. It is **only a hypothesis** that doing so would reduce local-choice anchoring or plan/action inconsistency. No completed comparison varies this order, and the observed rank/arithmetic/state errors are not explained by it. It should not be represented as their root cause or as a fix for bridge arithmetic; retain every existing failure and run a fresh, separately versioned candidate if pursued.

## Assessment

The primary observed cause in matrix v3 is playing-model reliability: despite adequate explicit instructions and decision-time facts, Luna Medium sometimes fails basic counting, rank comparison, follow-suit consumption, and state/history reconciliation. Current evidence does not identify a concrete snapshot assembly, schema parsing, or execution defect causing those outputs. The output-generation ordering inconsistency above is a genuine, bounded source-level inconsistency and a plausible experiment, not a proven release blocker or an acceptance waiver. Do not attribute errors to hidden missing facts, add a second reasoner/answer repair, or weaken the rubric based on these artifacts.
