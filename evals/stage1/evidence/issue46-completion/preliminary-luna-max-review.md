## Findings

1. **P1 — The production playing request does not establish an empty tool catalog.** `Sources/BridgeCodex/CodexTransport.swift:88-90` sends `turn/start` with input and output schema but no per-turn tool override. The current feature config disables many surfaces but does not remove generic tools (`:240-283`). The repository’s runtime test explicitly observes `exec`, `wait`, `request_user_input`, and `request_user_input_async` in the outbound `additional_tools` list (`evals/stage1/tests/test_runtime_isolation.py:78-88`), and the acceptance report disclaims an empty tool list (`evals/stage1/acceptance.py:414`). The offline tool-removal experiment showed an actual empty `additional_tools.tools` array using a Luna catalog override (`evals/stage1/evidence/issue46/offline-tool-removal-01/REPORT.zh.md:9-38`), but also says that candidate was not wired into the Bridge startup path (`:38`). Integrate the tested settings and assert the effective outbound list is empty before acceptance. The experiment was offline-only and does not establish service acceptance.

2. **P1 — Snapshot serialization drops decision-time context retained by `BoardState`.** `BoardState.snapshot` preserves `objective` and `publicBackground` (`Sources/BridgeEngine/BoardState.swift:69-81`); the CLI accepts/passes both (`Sources/BridgePlayCLI/BridgePlayMain.swift:9-18,34-41`); but `ExpertSession.snapshotInput` emits neither (`Sources/BridgeExpert/Expert.swift:178-203`). The fixed `DeclarerInstructions.txt` also has no definitions for these payload fields or for unknown auction/background agreements. Issue #36 requires supplied public background to reach the initial decision and retains the caller’s explicit objective; Issue #46 amends the delta-first mechanics while keeping other requirements. Therefore a provided background or non-default objective can silently affect neither model advice nor the exact model-facing record. Existing corpus fixtures all have null public background. The snapshot implementation agent has a pending fix for these fields; review it against #46’s static scoring sentence and the caller-context contract before integration.

3. **P2 — Evaluator does not correlate request and response evidence to the decision’s turn ID.** `evals/stage1/evaluate.py:72-76` passes `request_evidence` if the saved input occurs in any `turn/start`, and `output_evidence` if the saved raw output occurs in any agent-message completion. It does not require the two records to belong to the same turn or bind them to `record.identity.turnID`. `DecisionRecord` preserves that turn identity (`Sources/BridgeExpert/Expert.swift:71-84,171-175`) and transport logs the exact completion turn (`Sources/BridgeCodex/CodexTransport.swift:91-116`), so construction currently pairs them; however, the evaluator would not detect a misjoined/tampered multi-turn record. Harden this by correlating both evidence records to the recorded turn ID and exact request input/output. This is evaluator evidence integrity, not an observed live mismatch.
