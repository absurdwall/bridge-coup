# 新睿每日单副

使用 `mcp__cua_repl` 观察和操作新睿；从叫牌开始，通过同一 `bridge-external` 进程持续调用生产 Expert，完成首攻、做庄或防守。外层负责观察、解释预览、执行回执、claim 和总结。每次只绑定一副，完成记录与两类总结后退出。

## 绑定本次任务

先读 [每日配置](references/daily-task.md)，取得可持续使用的 Bridge Coup checkout、Codex runtime 和记录目录。缺少必要配置或桌面不可操作时，保存原因并报告未完成。正常登录、权限及账号由现有环境提供。

查看记录目录中的最近记录，再观察实际赛事。按**账号可辨识标签、赛事名称／平台日期、牌号**绑定，不以纽约日期代替新睿赛事日期。为新副生成一次 UUID 作为 Expert `boardID`，把映射保存在记录；接续时沿用。

- 有绑定牌的未完成记录：先核对同一副，按下文接续；不以新副代替。若已证实原赛事结束且记录标为不可接续，保留未完成与原因，不再点击旧建议；后续新日赛事按新任务绑定，不能把新副充作旧副完成。
- 本赛事本轮每日单副已完成：核对平台进度并返回原记录，不再开始下一副。不要因为结果延迟或重复唤起再开牌。
- 用户已手动推进：尊重当前平台进度。若遇到正在进行的牌，只有公开历史可核对才接续；无法确定与原记录的关系就保存并停止。不同日的新赛事可以绑定新副；跨日仍有未完成牌时先处理原副。用户另行明确授权的新一副手动验收，可绑定平台当前下一副；既有探索完成记录不授权重打旧副，也不扩展日程范围。
- 另一个运行仍在处理绑定牌：不并发操作，保留现状并报告。只在当前运行确认取得同副控制后行动。

首次绑定时复制 [中文记录模板](assets/board-record.md) 到仓库外，默认 `~/Documents/xinrui-daily-bridge/`，文件名含本地时间和牌号，避免覆盖。附件放同名 `-assets/`；记录实际路径、时间及时区。绑定、叫牌、每次实际动作、关键计划、claim 和结果随进展保存；不是等终局才写。

## 观察、叫牌和角色

打开 app 和操作前读 [新睿操作](references/xinrui.md)。从当前截图定位，观察后才操作。每个动作后重新读取实际状态；建议、预览、点击、动画均不是成功事实。每次下一决策或牌局操作前，先用当前截图／既有历史面板核对缺失的必要公开事实；仍无法确认时，保存最后确认事实与原因，标记未完成并停止，保留原副。

确认赛事、平台日期、牌号、进度、发牌人、局况、用户授权座位、计分和**双方当前实际体系**。当前使用 CCBA 也须现场确认，不写死；历史简易二盖一记录保持原标签。按花色记本手初始牌，核对 13 张唯一牌和 HCP。读 [Expert 调用](references/expert.md)，以本手及完整实际叫牌建立连续会话；轮到本手时请求生产建议。其他牌手仍由平台控制。接纳每个实际叫品前，收集公开 alert／解释，按 [实际叫品公开资料](references/expert.md#实际叫品公开资料) 与该事件一起交给入口；未知含义如实注明。完整实际叫牌及出处随进展保存。全 pass 时核对平台流局，不伪造打牌阶段；记录实际触发的叫牌 Expert。

Expert 返回解释请求或需要提交前核对候选时，按 [解释预览与回传](references/expert.md#解释预览与回传) 服务指定少数候选。只读预览，不先点遍合法叫品；资料回传后再取得最终候选及新授权。解释中文原文、来源与适用疑问分别保留；无命中／不可用是正常结果。

叫牌结束后核对实际定约、倍数和庄家，再向同一会话确认，保持 boardID 与玩家历史。首攻前只提供本手和公开叫牌／定约；实际首攻后才加入曝光手牌。MP 目标考虑超墩，正式目标与分析指标分开。

- **我方或对家做庄**：controller 切为实际庄家，生产 Expert 控制庄家与明手；从明手出牌时 acting seat 是明手。实际可见后补齐需控制的庄家和明手完整初始牌；对手暗牌保持未知。
- **我方防守**：首攻和后续选择均由生产 Expert 决定，只控制用户授权一家。明手曝光后可见但不受控；对家及庄家暗牌未知，其他牌手行动记平台来源。

## 建议、执行、确认

维护完整实际叫牌、公开解释、实际牌序、当前墩、已完成墩的赢家、累计墩数、可见手牌余牌及缺门。事实与推断分开；历史面板的上一墩不覆盖当前墩。自动行动也按实际顺序记录，不从计划推演牌序。

连续循环：接纳新的真实平台事件 → `decide` → 服务可能的资料请求并再次 `decide` → 按最终授权的座位／叫品或牌操作 → 重新观察实际行动 → 带该候选 authorization 用 `observeCall`／`observe` 确认 → 保存。查询、preview、review 和授权都不推进实际牌局。平台在请求建议前已自动打出的唯一合法受控牌，按 [Expert 调用](references/expert.md) 的 `automatic: true` 分支确认并记 forced；不虚构建议。首次实际 Expert 选择建立计划，所有有选择行动通过生产 Expert；手动 forced 建议仍带入口授权确认。外层不能因不同意建议而换牌或把公开计划编译成跳过 Expert 的执行策略。

记录当前 phase／指令版本、候选 ID、advice、authorization 和实际确认的关联，以及查询来源、decision 文件、公开计划变化、真实 reviewer verdict 和 executionDisposition。`contested` 是既有政策下的执行授权，不能写成 approve。生产 player 和独立 reviewer 沿用既有配置；外层聊天模型设置不改变它们。入口失败或关键事实无法核实时，保存原副、已有 evidence 和原因并报告未完成。外层不代做已支持的叫牌／首攻／做庄／防守来冒称 Expert 成功，不换副掩盖失败，不绕过 review 或重启规避限额。

## Claim 与终局

Claim 由外层 Codex 判断：写明当前双方已得墩、剩余墩、申请墩数及从决策时信息可证明的路线，同时检查可争取的超墩。不确定则继续出牌。核对界面申请数和对应结果后提交，保留 Expert 进程直到平台确认终局。

- 接受：记录实际接受和服务器最终结果；真实牌序到实际最后一张为止，claim 分配的余墩另记。
- 拒绝或取消：记录结果，重新观察同副当前状态；把新增实际牌按序交给入口，继续正常打牌。尚无终局时不 `stop` 入口，不重发旧点击。
- 结果尚未更新：等待并重新读取同副结果／赛事进度，不点击“开始打牌”来刷新，不进入下一副。

全打完、claim 接受和全 pass 都以平台结果确认完成；保存证据。只做完操作却没确认结果，状态仍为未完成。

## 比较、总结和交付

终局后读实际可用的同牌比较、代表桌回放和双明手分析；全牌此时才可读入赛后分析。记录选了哪桌、看到了哪一墩／哪段叫牌及结果；数据不可用则写不可用。全牌可得时核对四家各 13 张、共 52 张唯一牌。单副分数／MP／排名与整场指标分别记录并说明视角。

完成模板中的两类总结：

- **打法总结**：公开计划与转折、可疑选择和可执行替代；分清当时事实／推断、赛后暗牌／DD、对手帮助和运气、尚未确定的因果。不同首攻或叫牌的高分桌不能直接证明本桌选择错了。好成绩与 review 通过都不证明棋力。
- **流程总结**：具体读牌、重复观察、失败点击、app 定位、接口请求、claim、结果延迟等摩擦及临时处理；记录原始证据位置、实际耗时、实际打出的完整墩／未完墩和 claim 数。后续工具／知识／评测候选只记候选，不自动改代码或配置。

读回已保存 Markdown 和所引用的本地材料，核对绑定、牌序、来源、结果、总结、未确认信息及接续状态。成功后 `stop` Expert，退出新睿并从 app 状态确认已退出，更新记录。异常时保留牌局及材料，记录 app／进程实际状态，避免通过放弃牌局强行收尾。向用户返回完成／未完成、关键结果、一条发现和可打开的绝对路径记录链接。

## 基本接续

先读最新记录和其引用的最新 `continuation.json`，再观察同一赛事／牌号、实际叫牌、阶段、定约／曝光状态、当前墩与历史墩、已打牌、可见余牌及平台结果。逐项核对后才继续。

原进程仍在、健康且状态匹配时延续它；待资料回传也使用原请求 ID 和准确上下文。若有当前有效待执行建议，仍按其 authorization 执行并观察确认。此时 checkpoint 的 unsafe 只禁止重建，并不自行撤销原进程有效授权。需要新会话时，只有最新 checkpoint `safeToResume: true` 且 configuration 与实际核对完全一致，才能按 [Expert 调用](references/expert.md) `resume`。记录新会话重建及证据链；不恢复旧 thread、点击、坐标或 authorization，不回退更早的 safe 文件来覆盖最新 unsafe 状态。新增实际事件按序输入。

旧 v1 做庄记录按原协议核对，不改造成从叫牌开始的证据。缺少初始可见手牌／真实完整历史、待确认建议无法消歧、需要重建但最新 checkpoint unsafe、平台已换副、入口失败／超限等情况，保存最后确认事实、缺口、附件与 app 状态，报告未完成；不猜补事实、不默默开启另一副。入口保留既有单请求和整副限额，接续不能重置绝对截止时间。
